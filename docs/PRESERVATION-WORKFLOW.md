# Preservation and restoration workflow

Blacklight uses this six-stage model to keep evidence, permission, restoration work, and results understandable. The dedicated Recovery System is under development; this guide does not claim every stage is already automated.

| Stage | Work and completion evidence |
| --- | --- |
| Discovery | Record the lead, source, time, and uncertainties. |
| Verification | Review the evidence and establish owner approval for the exact target and planned work. |
| Documentation | Preserve originals, define scope, document damage, and record before images and available baselines. |
| Recovery | Work on an isolated copy, assign helpers, log changes, and retain a rollback point. |
| Validation | Compare the repaired result to the agreed baseline and scope; obtain owner review and test restoration. |
| Archive | Retain the approved artifact, hashes, coverage limitations, before/after evidence, and validation receipt. |

## Keep facts separate

Public status responses, account-specific admission, owner identity, preservation permission, and backup completeness are different facts. A successful join by one account does not establish that the whitelist is disabled. Unknown data remains unknown. Player activity and stream links are leads, not proof of ownership or wrongdoing.

Before capturing or changing a world, record who approved the work, the target, permitted method and area, output handling, and any expiry or revocation. Private project access does not supply another owner's permission.

## Record an incident

Use a stable case identifier and record the affected world or approved target, discovered time, observed damage, evidence references, approved helpers, priority, progress, and next action. Keep original evidence and distinguish reported facts from independently checked facts. Do not infer an attacker from terrain damage alone.

Useful metrics include blocks restored, structures repaired, cases closed, and time to recovery. Label estimates and manual declarations clearly. Mark a case closed only when its declared recovery scope has passed validation; do not count a copied file as a successful restore.

## Contact and disclosure

Review warning drafts before sending them. Ask whether access was intended to be public or private without posting the server address or sensitive evidence in a stream chat. Agree on a private contact path and offer practical help. Keep private reports outside public GitHub issues.
